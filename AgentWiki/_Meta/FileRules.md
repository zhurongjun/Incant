# 知识文件与内容规则

## 文件组织

- 文件和目录使用大驼峰命名；导航文件统一为 `index.md`，元知识目录沿用 `_Meta`。
- 目录通常提供索引；没有索引的目录视为叶子目录，按文件名定位内容。
- 叶子文档主题明确、名称准确。按职责分组，不为每条规则单独建文件。
- 同一规则只保留一个维护位置，其他文档通过链接引用。

## 内容边界

- 长期规范描述明确的项目约定；项目知识描述特定领域的事实及适用范围，两者应清楚区分。
- 临时限制、排查过程、失败日志、验收结果和未确认设计属于任务记录，不写入长期规则。
- 不因完成一次修复自动追加永久约束，也不把一次任务的运行范围写成所有后续任务的要求。
- 确需保存项目知识时，放入对应专题，说明适用范围并链接代码、测试、配置或已确认的设计来源。
- 对版本、项目清单和运行配置优先引用实际来源，避免复制容易过期的完整列表。
- 修改规则语义需要明确依据；不能把文字整理变成未经确认的新约定。
- 代码和配置用于核实事实，不能用当前实现中的偏差静默覆盖明确规范。发现冲突时说明差异及依据。
- 外部参考应按本项目实际情况取舍，不将参考仓库的语言、命名或工具约定直接变成本项目规则。

## 维护检查

- 检查每段新增、修改及删除内容是否符合文档职责，是否夹带任务状态或重复约束。
- 移动、重命名或删除文档后，核对原文去向并更新引用，避免遗留重复副本。
- 对涉及索引的变更，执行 [索引规则](IndexRules.md) 中的导航检查。
- 查看完整 Markdown 差异，执行 `git diff --check`；新增的未跟踪文件也应纳入检查。
