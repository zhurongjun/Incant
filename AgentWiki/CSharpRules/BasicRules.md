# C# 基础规则

## 适用范围

本规范适用于仓库内所有人工维护的 C# 代码。

本规范以微软的通用 C# 编码约定、.NET Runtime 编码风格和仓库根目录的 `.editorconfig` 为依据：

- [通用 C# 编码约定](https://learn.microsoft.com/dotnet/csharp/fundamentals/coding-style/coding-conventions)
- [C# 标识符命名规则和约定](https://learn.microsoft.com/dotnet/csharp/fundamentals/coding-style/identifier-names)
- [.NET Runtime C# 编码风格](https://github.com/dotnet/runtime/blob/main/docs/coding-guidelines/coding-style.md)

`.editorconfig` 是可自动检查规则的执行配置，本领域文档补充无法由工具完整表达的语义、可读性和人工验收要求。两者冲突时，应先查明原因并同步修正，不能静默忽略其中任意一方。

## 基本原则

- 正确性和可读性优先于代码简短或技巧性写法。
- 使用当前目标框架支持的现代 C#，避免已经过时的语言结构。
- 一个类型、成员或变量应使用能够表达其职责的名称。
- 保持变更范围紧凑，不在功能修改中夹带无关的格式化或重构。
- 修改既有代码时，应使触及的代码符合本规范；如果兼容性要求阻止修改，应在代码或任务说明中记录原因。

## 特殊情况

- 自动生成代码不进行人工风格重写，应在生成器或模板源头修正。
- 与外部 API、原生接口或序列化格式绑定的名称可以保留外部命名，但应将例外限制在边界层。
- 为保持公开 API 或数据格式兼容而不能重命名时，应记录兼容性原因。

## 编码前检查

开始新增或修改 C# 代码前：

1. 读取本文件，再按任务读取 [代码组织](CodeOrganizationRules.md) 和 [代码书写](CodeWritingRules.md) 中的相关规则；不得只依赖记忆或格式化工具。
2. 阅读仓库根目录 [.editorconfig](../../.editorconfig)，确认自动执行的格式和命名规则。
3. 检查将要修改的类型及相邻代码，了解现有契约、异常策略和所有权关系。
4. 在写代码前确定新增类型、成员、字段和参数的名称，确保符合命名规范。

## 退出验收

完成 C# 变更后，先列出适用的规则项目，再分批审查，每批只检查一个规则类别。完整差异中的每个区块，以及其中每个新增或修改的类型、成员和独立逻辑块，都必须接受适用规则的检查。

依次检查以下类别，不将所有类别合并为一次笼统检查：

1. **文件与格式**：编码、缩进、换行、大括号、空格和 `using` 布局正确。
2. **命名**：类型、成员、字段、常量、参数和局部变量符合对应命名规则。
3. **类型使用**：关键字类型、`var`、空值和 `readonly` 的使用符合规范。
4. **结构与表达式**：修饰符、命名空间、初始化、模式匹配和表达式形式清晰一致。
5. **控制流与资源**：异常、异步、取消、释放和所有权处理正确。
6. **注释与 API**：注释仍然准确，公开契约及兼容性例外得到说明。
7. **变更边界**：没有夹带无关重排、格式化或重构。

人工逐项验收后，还必须：

- 查看完整 C# 差异，确认没有遗漏的代码段。
- 对受影响的项目运行 `dotnet format <项目> --verify-no-changes --no-restore`。
- 构建受影响的项目；条件允许时构建 `Incant.slnx`。
- 运行与改动相关的测试或可执行验证；测试执行范围遵循 [单元测试指引](../Testing/UnitTesting.md)。
- 修正发现的风格问题；无法执行的检查或必须保留的规范例外，在最终说明中明确列出，不得在未完成验收时声称代码风格正确。

格式化、分析器、构建和测试只能证明自动化部分通过，不能替代上述人工验收。
